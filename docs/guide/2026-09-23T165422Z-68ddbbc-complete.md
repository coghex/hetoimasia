[`tools/flake/process.py:99`](https://github.com/coghex/hetoimasia/blob/68ddbbce1f25794b576331bb3b2b711cf3ec255e/tools/flake/process.py#L99).

catches only `ProcessLookupError`; the outer catch at line 103 overwrites the
already-set timeout with `harness-error`. `measure` then treats that as a
blocked batch rather than a recorded workload timeout.

A controlled Darwin reproducer starts one owned session leader, registers
kqueue NOTE_EXIT before releasing its input gate, and observes exit without
reaping. `ps` reports `Z`; calling the production `group_exists` raises
`PermissionError(1)`. Reaping that same child makes the call return `False`.
No timing sleep is required for this causal check. Apple's
[process-group signal implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c)
also shows zombie filtering and an EPERM result when a found group's iteration
finds no eligible process. That is supporting explanation, not a claim that the
online source is this machine's exact kernel build.

The instrumented timeout case's owned group had no members by the subsequent
process-table observation. This establishes result misclassification; it does
not establish that an owned process survived or authorize treating every EPERM
as harmless. Genuine permission failures must still fail closed.

Environment: macOS 26.7.1, arm64, Python 3.14.6. Original fixture failed in the
full suite and focused run; two traceback/observation copies also failed.
Instrumentation is retained only in the ignored evidence directory. No
production fix was applied and no passing retry replaces these observations.
