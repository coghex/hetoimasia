## Findings

### [#727] GUIDE-1. Keep subprocess-group identity reserved through cleanup signals

**Disposition:** repair. **Verification:** static control-flow and OS-contract risk; no unrelated process was signalled and no PID-reuse experiment ran. **Principles:** V-3, V-10; #588's accepted no-unreserved-identifier amendment, comment 6569447216.

**Evidence:** [Subprocess.hs:978](https://github.com/coghex/hetoimasia/blob/b800f2fe9f81e3daaa53222759293fd17b97d04d/tools/test-support/src/Test/Support/Subprocess.hs#L978) reaps the direct child before drain and release. `endGroup` at lines 744–782 probes the numeric group and signals it when present; `probeFor` at 789–797 remembers only an absence it actually observed. [OwnedSubprocess.hs:601](https://github.com/coghex/hetoimasia/blob/b800f2fe9f81e3daaa53222759293fd17b97d04d/tools/test/OwnedSubprocess.hs#L601) tests absence **before** reuse.

**Consequence:** the original leader can be reaped, its group empty, and the number reused before the first cleanup probe. That probe sees the unrelated group and cleanup sends it TERM/KILL. A positive probe also cannot reserve an identity until the later signal. This inference follows the code and the [kill](https://man7.org/linux/man-pages/man2/kill.2.html), [waitpid](https://man7.org/linux/man-pages/man2/waitpid.2.html) and [identifier lifetime](https://docs.oracle.com/cd/E19620-01/805-3174/6j31do6c5/index.html) contracts; frequency is unmeasured.

**Action:** preserve a stable reservation through every possible signal, or use another race-free ownership mechanism. A second existence probe is insufficient. Preserve descendant cleanup, bounded observation, reaping and failure evidence. Closed #588/#603 fixed the distinct observed-absence-then-reuse schedule; no open issue covers this residual case. Current-head recheck found the relevant code unchanged.

Title: **Reject noncanonical reconstructed terrain component origins**

Labels: none.

```markdown
## Background

At master e49f4e233a15cdd80bc1473e7f704e44d0e29632, the public component-key reconstruction API admits values that the compiled connectivity queries interpret inconsistently.

In packages/terrain/src/Hetoimasia/Terrain/Internal/Connectivity/Index.hs, keyOf/nodeOrigin (:313–326) always produce the representative box's origin. mkComponentKey (:175–188) reconstructs an origin and ordered parameters without a compiled source, intentionally leaving semantic validation to consumers. However, resolve and resolveRep (:347–377) check only that the supplied origin lies in the representative node and that parameters fit, not that it is the representative's canonical origin.

Concrete source trace: compile a wholly air source, obtain its canonical key, move the key origin one cell in X inside the same representative box, and reconstruct with the original empty parameters. The altered key differs from the canonical key. isExterior accepts it as Just True and componentRanges supplies its ranges; componentContains returns False even for a tile in those ranges because componentOf produces the canonical key. With an empty discovery provider, queryNodeClass accepts SrcNode of the altered key as a separate implicit root, and queryComponentKnown treats it as exterior through isExterior (Internal/Discovery/Core.hs:443–448,1128–1143).

This violates the canonical component identity and consistent membership contract. It uses air only, so the pending slope-model decision does not block the repair. The temporary-store decoder also calls mkComponentKey, but ordinary encoding was not shown to produce aliases and no disk-corruption incident is claimed. No probe ran during the guide review.

2. Preserve the public reconstruction inverse for valid keys: mkComponentKey (keyOrigin key) (keyParameters key) must still return the same key. Keep reconstruction independent of a compiled source; it may produce a syntactically valid value that source-dependent queries subsequently refuse. Preserve parameterized families and the existing rejection of invalid parameter lists.
```
