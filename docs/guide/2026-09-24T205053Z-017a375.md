## Findings

### [#258] GUIDE-1. Read graphics-owner destruction and completion coherently during shutdown

**Disposition:** repair. **Verification:** confirmed by code and a controlled
production-path scheduling experiment. **Principles:** V-3, V-4 and V-5.

[Owner.hs:2014](https://github.com/coghex/hetoimasia/blob/017a375073119553c3289020f9ae15c7a9ff3273/packages/glfw/runtime-glfw-core/Hetoimasia/Runtime/GLFW/Internal/Owner.hs#L2014)
reads `ownerDestructionVerified`; line 2022 separately reads `ownerRunEnded`.
Both derive from the same `OwnerTerminal` cell, but across transactions.
The owner records destruction at line 1596 before recording completion at line
1090. A legal ordering is:

1. Main thread reads destruction as false.
2. Owner publishes successful destruction, then completion.
3. Main thread reads completion as true and calls `declareUnverified`.
4. The next loop sees verification and joins, but `finishOwnerExit` retains and
   raises the false `OwnerDestructionUnverified` afterwards.

This causes a false warning and failed application exit after successful
cleanup. It does not authorize early release. The code predates this batch;
PR #257's solver explicitly reported it, and its new consumer is the reason
this audit reopened the previously covered owner path. A more realistic event
wait reduces exposure without making the two reads coherent.

The untouched integration suite passes 26 examples. In the unique detached
review checkout, temporary STM barriers held the owner before publishing
successful destruction, let the main thread perform its first read, and then
let the owner publish destruction and completion before the second read.
The existing no-attachment example failed with
`OwnerDestructionUnverified {unverifiedRetired = True, unverifiedTargets = 0}`.
Keeping the same barriers and reading both decisions in one transaction made
that example pass. This is instrumented production-path evidence, not a claim
that an unmodified run failed. Both patches and logs are retained locally;
the source was restored byte-for-byte, and no repair was committed.

Existing genuine-unverified examples in `Test.GLFW.Owner` intentionally wait for
completion without destruction and require retained parents plus independent
evidence. They must remain valid. The eventual regression belongs beside those
examples, with a private seam or production decision boundary rather than the
experiment's temporary process-global barrier.

**Dedup:** Complete open inventory and three open/closed searches found no repair
issue. #218 delivered the affected machinery; #219/#257 disclose but do not fix
it. #220 migrates the native fixture. #227/#231/#232 concern subsequent GPU
completion, failure and scheduling; none specifies repairing this existing
mixed-observation branch. Their implementation need not be pulled into this fix.

The owner-approved body filed on GitHub follows.

````markdown
## Background

At `master@017a375`, `awaitOwnerDestruction` in `packages/glfw/runtime-glfw-core/Hetoimasia/Runtime/GLFW/Internal/Owner.hs` reads destruction verification and owner completion in separate transactions. This permits the following ordering:

1. The shutdown thread reads destruction as unverified.
2. The graphics owner publishes successful destruction, then completion.
3. The shutdown thread reads completion as true and records `OwnerDestructionUnverified`.

Consequently, successful teardown can produce a false warning and failed application exit. The retained failure is raised after joining; this finding does not demonstrate premature resource release.

PR #257 reports this race. The guide audit confirmed it using temporary STM barriers around the production publications and reads: an otherwise successful headless exit failed with `unverifiedRetired=True` and `unverifiedTargets=0`. Reading both facts from one coherent terminal snapshot passed under the same forced ordering. The instrumentation was restored afterwards; it is not a committed regression test.

## Requirements

1. Decide whether destruction is verified and whether the owner ended from a coherent observation. Successful destruction followed by completion must not produce an unverified-destruction warning or failure through mixed observations.
2. Add deterministic regression coverage in the GLFW-owned headless suite, alongside `packages/glfw/test/Test/GLFW/Owner.hs`, exercising the production decision. The regression must detect the old behavior and verify that successful teardown produces neither the false warning nor the typed failure.
3. A minimal private coordination seam or private production decision boundary is permitted where needed for deterministic coverage. Keep it inaccessible to consumers. Do not introduce global test switches, duplicate the lifecycle implementation, or rely on sleeps or lucky scheduling.
4. Preserve genuine unverified-exit behavior: report once, retain dependent resources, await independent destruction evidence, and join before final host disposal. Preserve primary failures, distinct cleanup evidence, and cancellation handling. Worker completion alone must never authorize release.
5. Deliver code, tests, and any necessary updates to owning comments or `docs/glfw.md` together in one PR.

## Acceptance

With the repository’s qualified GHC/Cabal toolchain and provisioned GLFW SDK:

```sh
cabal test hetoimasia-glfw:glfw-tests --test-show-details=direct
python3 tools/validation/plan.py --base origin/master --head HEAD
```

The new regression detects the previous mixed-observation behavior and passes with the repair. Existing genuine unverified-destruction, cancellation, and join-order examples remain green.

Complete the validation planner’s required checks before review. The regression requires no native desktop session.

## Out of scope
````
