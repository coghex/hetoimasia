## Findings

### [#155] GUIDE-1. Choose rendering ownership after the measured Cocoa stalls

**Disposition:** owner decision. **Verification:** measured evidence and current
call order verified. **Principles:** V-2, V-3, V-5, V-6.

[The verdict](../owner_loop_interaction_verdict.md#what-the-owner-has-to-decide)
requires a policy decision before VK-16. The main-thread event pump can remain
inside Cocoa for the duration of a resize or menu interaction. Shortening the
idle timeout cannot promise owner-turn progress. The queued command and
reconciliation paths remain on that owner; this run does not establish progress
for another renderer, another window, simulation or the scheduled loop.

**Recommendation for discussion:** design a separate supervised graphics owner
before VK-16, retaining main-thread GLFW ownership and record-only callbacks.
Treat this as a bounded design revision, with explicit cross-thread geometry,
render-demand and lifetime handoffs, queue ownership, cancellation and final
retirement. Rendering on another thread would not make main-thread window
commands continue during the modal loop, and current callback observations are
not published until reconciliation; those limits must be designed explicitly.
Do not start moving code or imply this policy is already approved.

**Reasonable alternative:** explicitly accept owner-driven rendering pauses for
the first integration and retain the measured limitation, revisiting the worker
boundary in a later named arc. A callback-driven redraw is a third option in the
verdict, but it changes callback safety contracts and does not address the menu
case where callbacks do not arrive during the stall.

**Exact proposed decision for owner approval:** “Keep GLFW operations and
record-only callbacks on the process main thread. Before VK-16, specify a
separate supervised graphics owner with explicit data and lifetime handoffs;
do not infer that this permits off-thread GLFW calls or guarantees window-command
progress during a platform modal loop. VK-4 and other independent prerequisite
work may continue while this design is settled.”

No new tracker issue is proposed before this ownership choice is settled.
The existing #200 delivery measured the problem and deliberately chose no policy.

### [#224] GUIDE-2. Restrict stall descriptions to owner-driven application work

**Disposition:** documentation drift, small mixed comment/docs correction.
**Verification:** verified. **Principles:** V-1, V-2, V-5.

At `8b2fcfd`, [the probe comment](https://github.com/coghex/hetoimasia/blob/8b2fcfdbb30ab7856ca5b44fb445aa05b56cced0/packages/glfw/native-tests/Test/GLFW/Native/Interaction.hs#L7-L8)
says “nothing the application owns progresses” and
[the GLFW contract](https://github.com/coghex/hetoimasia/blob/8b2fcfdbb30ab7856ca5b44fb445aa05b56cced0/docs/glfw.md#L4378)
asks whether “anything the application owns progresses.”
The inference bullet in [the verdict](https://github.com/coghex/hetoimasia/blob/8b2fcfdbb30ab7856ca5b44fb445aa05b56cced0/docs/owner_loop_interaction_verdict.md#L206) similarly
states that simulation stops, although the later alternatives correctly make
that conditional on owner-driven simulation.

The measurement records the owner loop, not every application worker. The
runtime permits separately supervised work, and the vision specifically allows
independent UI/gameplay execution. The evidence therefore proves that owner-loop
reconciliation, dispatch and update hooks do not advance, not that every
application-owned computation stops. This wording must not become a premise for
subsequent threading design.

**Proposed bounded issue:** “Qualify owner-loop stall descriptions to the work
they actually measure.” Replace the two blanket statements with “owner-driven
application work”; qualify the simulation inference as simulation executed by
`loopUpdate`. Preserve the measured numbers, raw evidence, ownership policy,
consent gate and runtime behavior. Keep the source comment and companion docs
in one PR. Acceptance is inspection of those passages against the existing loop
order; no new desktop evidence or behavior tests are needed for this wording-only
change. #211 concerns Vulkan presentation comments and #212 concerns platform
selection, so neither currently owns this correction.
