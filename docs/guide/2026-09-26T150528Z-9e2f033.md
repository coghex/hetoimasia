**Disposition:** owner decision.
**Verification:** verified.
**Principle:** V-2 (build infrastructure methodically) and V-11 (efficient solo
delivery); [module conventions](../module_conventions.md), "Delivery and choices
still to settle".
**Evidence:** The conventions record two 2026-09-26 owner decisions. The priority is
to "finish the structural refactors before returning to the feature backlog". The
sequencing is to first refactor existing code into the flexible `Base`/`Types`
layers, with the GPU-model `State.hs` decomposition after that. The same section
says "the exact package scope and delivery slices still need an implementation
plan", and it defines a file over 600 lines only as a refactoring *candidate*. At
the pin, 28 production Haskell files exceed 600 lines, from
`GPU/Model/Internal/State.hs` (3,003) and `Runtime/GLFW/Internal.hs` (2,827) down
to `Runtime/GLFW/Internal/Surface.hs` (688); the list is saved in this run's local
evidence as `oversized-production.txt`. #266 is approved, open and unstarted,
and nothing places it relative to the `Base`/`Types` refactor.
**Consequence:** Until a plan exists, the phase has no end condition. Read as
"every candidate", it holds #225–#233 back behind about 28 refactors, most of them
in GLFW code the Vulkan arc doesn't touch. For #266, a solver could start the
generation split before the layers it should follow exist. The split would then
be redone, or it would set a private-module shape the `Base`/`Types` refactor has
to work around.
**Action:** Write the owner's implementation plan as a design document (the
`design-epic` workflow fits: it records scope, ordered slices and open questions
before any issue is filed). It needs three answers:

1. **Scope:** which packages the `Base`/`Types` refactor covers. Recommended: the
   packages the Vulkan arc builds on (`gpu-vulkan` model, native and glfw), with
   other packages' oversized files staying candidates that are split when an
   issue next changes them, as the conventions already allow. Alternative: every
   package, which takes much longer to deliver.
2. **#266:** proceed now as an independent private-module split (recommended: it
   moves code without changing layers, as #265 did, and the layering refactor can
   build on its smaller modules), or wait and be amended to apply the layers.
3. **End condition:** the list of issues whose merge ends the phase and resumes
   #225.

No tracker change is proposed until the owner answers.

## What moved

- **PR #267 / #265: recording split.** `Recording.hs` went from 1,817 lines to a
  263-line facade over `Internal.Recording.{Layer, State, Construction, Recorder,
  Batches, Readback, Disposal}` (the largest is 560). The import graph is acyclic:
  `Layer` ← `State` ← {`Construction`, `Batches`, `Readback`, `Disposal`}, and
  `Recorder` takes `Batches`. Cabal keeps every new module under `other-modules`.
  The public Haddock's state table now names `State`, `Construction`, `Recorder`,
  `Batches`, `Readback` and `Disposal` as the actual readers and writers.
  `docs/gpu_backend.md` gains the module inventory and a "How the recording is
  built" section. Recording code already has headless and native coverage;
  `RecordingVisibility` adds boundary evidence, with one accepted client importing
  all 54 public names, seven hidden-module rejections (`GHC-87110` naming the
  unit, never an environment failure) and six rejections of abstract handles'
  constructors (`GHC-10237`).
- **#266: generation split.** Approved, open and unstarted. The file is unchanged
  since the issue's base (`Generations.hs` is still 1,122 lines), so its anchors
  hold. Its review amendment said #265 couldn't be read; #265 has now merged, so
  the "whichever lands second rebases" rule resolves to #266 preserving #267's
  Cabal, README and `gpu_backend.md` entries. Following #267's
  `Internal.Recording.*` pattern (`Internal.Generations.*`, a small
  `…Visibility` test module in `RootsMain.hs`) would keep the two splits alike;
  the spec leaves names to the solver.
- **Other open issues** (#145, #155, #202, #207, #225–#233) have unchanged
  fingerprints and none cites a recording or generation line anchor, so the split
  leaves no stale references.
