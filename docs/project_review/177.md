## 1. Platform-specific validation

### PRR-1. Make the Linux-only validation obligation executable on its eligible platform

> **Captured note:** P2 — PR #177 registers the Linux confinement probe as a
> mandatory affected group for every runner OS, although its Cabal components
> are unbuildable on Darwin. An affected Darwin validation plan consequently
> requires an execution it cannot complete. Preserve conservative input coverage
> while giving the platform-only obligation a satisfiable execution policy.

**Verification:** At the verification commit on macOS, the planner command
below exited 0 and selected `test.lua-confinement-linux` with
`runner_os: Darwin`, `selected: true`, `inputs_changed: true`,
`reason: affected`, and `optional: false`. Routing all selected groups except
that Linux-only group exited 2 because it had no worker. Running its prescribed
Cabal test command with qualified GHC 9.14.1 and Cabal 3.18.1.0 exited 1 with
`[Cabal-7043]`, saying the suite was `buildable: False`. The group is therefore
neither executable locally nor omittable from the routed Darwin plan. Existing
receipt compatibility includes `runner_os`, so a Linux execution cannot supply
the missing successful Darwin receipt.

**Evidence:**

- `tools/validation/catalog.json:174` introduces the Linux-only group and its
  unconditional CPU command; line 192 makes it non-optional without declaring
  execution-platform eligibility.
- `tools/validation/plan.py:1031` derives selection from affected inputs,
  optionality, requests, and the floor. The non-optional affected group is
  selected without considering the plan's runner OS.
- `packages/scripting-lua/hetoimasia-scripting-lua.cabal:350` correctly excludes
  `linux-confinement-probe` outside Linux. The child has the same exclusion at
  line 316; making either build on Darwin is not the correction.
- `tools/validation/plan.py:1074` checks worker coverage of selected groups and
  refuses a routed plan that omits this obligation.
- `tools/validation/receipts.py:45` includes `runner_os` in evidence compatibility;
  `tools/validation/run.py:853` records the executing OS. A differently named
  Linux worker does not make its receipt satisfy a Darwin plan.
- `docs/validation.md:178` explicitly documents platform-independent source
  coverage and selection. This confirms the behavior was deliberate, but leaves
  the execution conflict unresolved.

**Handoff context:**

- **Current behavior:** On Darwin, a change affecting this group's closure or
  declared inputs produces a mandatory Linux-only execution. Assigning it to a
  local CPU worker leads to Cabal's disabled-component failure; leaving it
  unassigned prevents a runnable plan. This affects local validation plans even
  though the Linux CI worker can run the group successfully.
- **Expected behavior:** A plan for a supported runner platform must have an
  executable account of its selected obligations. Preserve Linux's mandatory
  affected-group coverage and explicit worker assignment. On Darwin, account
  honestly for the group's platform inapplicability or route a separately
  identified Linux obligation through a supported platform-aware mechanism.
  Do not fabricate a passing Darwin result for a component that cannot build.
- **Scope and constraints:** This is an integration/design gap exposed by the
  new mandatory Linux-only group, rather than a failure to implement #147's
  owner-approved parser amendment. That amendment deliberately preserves input
  coverage on both platforms; input derivation and fingerprints must remain
  conservative even when execution eligibility differs. Do not make the Linux
  probe globally optional, weaken unknown-input fallback on Linux, weaken OS
  receipt identity, or alter the mandatory floor. Keep the confinement verdict
  and Linux build exclusion honest.
- **Verification target:** Add focused workflow Hspec coverage for the same
  affected candidate planned for Linux and Darwin: source changes are recognized
  in both, Linux still requires and routes the probe, and Darwin has no selected
  obligation whose only command targets an unbuildable component. Exercise
  routing and receipt/aggregate handling for the chosen policy, plus unknown
  inputs and shared dependency changes. Preserve rejection of unsupported
  dependency-changing Cabal conditionals. No native desktop session is needed.
- **Deduplication:** The open issue inventory and all-state searches for
  `"Darwin" "validation"` and `"confinement" "planner"` found no dedicated
  repair. #147 is the closed originating issue; #148 is the separate macOS proof
  and #145 is the open Lua umbrella. The claimed ledger row had no earlier
  report or finding links.
- **Remaining uncertainty:** The preferred representation of platform
  eligibility or cross-platform obligations needs a deliberate workflow design.
  The demonstrated Darwin selection/routing/execution conflict is not uncertain.
