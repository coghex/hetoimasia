## 1. Image availability and presentation retirement

### PRR-1. Allow image reacquisition while an earlier presentation record remains pending

> **Captured note:** P2 — `acquireImage` rejects an image whenever any live
> presentation-pool record names it, even after presentation was enqueued and
> the rendering submission completed. This adds the image-specific host wait
> that accepted P-2 explicitly removed. Admit a successful reacquisition into a
> distinct free record while retaining the previous presentation's obligations.

**Verification:** At the verification commit, a public-API sequence publishes
two images, acquires image 0, submits and enqueues its presentation, records only
rendering completion, and reserves another frame and pool record. Reporting a
successful reacquisition of image 0 is rejected as `AlreadyConsumed ImageIdentity`.
The previous presentation is still tracked, as required; its existence should
not itself reject the new acquisition. The Hspec reproduction exits 1 with
`1 example, 1 failure` at the final admission. No GPU is needed to exercise this
pure contract.

**Evidence:**

- `docs/vulkan_backend_design.md:881` requires a finite pool of independent
  presentation synchronization records. Lines 889–899 expressly allow image
  reacquisition without a host wait for the previous present fence when another
  pool record is free; the new acquisition synchronization still must be obeyed.
- `packages/gpu-vulkan/model/src/Hetoimasia/GPU/Model/Internal/State.hs:1450`
  rejects acquisition through `imageOwned`. Its definition at line 1502 checks
  every pool entry with the same generation/image, without distinguishing an
  already-enqueued present from an unpresented image still owned by a frame.
- `packages/gpu-vulkan/model/test/Test/GPU/Model/Frames.hs:200` expects that
  rejection after submission completion. The fixture in
  `packages/gpu-vulkan/model/test/Test/GPU/Model/Support.hs:156` chooses an image
  absent from every outstanding presentation, so other sequences avoid the
  accepted reacquisition case.
- `docs/gpu_model.md:120` states the same incorrect restriction. This was added
  in response to an early PR review comment, but that comment did not amend the
  accepted P-2 design. Agreement among code, tests and implementation prose does
  not resolve their conflict with that design.

Save this exact reproduction as `Reacquire.hs` outside the checkout. The existing
`Test.GPU.Model.Support` helpers construct fixtures through exposed model APIs:

```haskell
{-# LANGUAGE GHC2024, UnicodeSyntax #-}
module Main (main) where

import Hetoimasia.GPU.Model
import Hetoimasia.GPU.Model.Budget
import Test.GPU.Model.Support
import Test.Hspec

main :: IO ()
main = hspec $ describe "P-2 image reacquisition with distinct presentation records" $ do
  it "admits a new acquisition without retiring the previous present's record" $ do
    model <- freshModelWith defaultBudgetRequest {requestedImageTracking = 2}
    (active, target, _) <- activeTarget 2 model
    (reserved, frame) <- admitted "reserve first frame" (reserveFrame target active)
    (acquired, _) <- admitted "acquire image zero" (acquireImage frame (AcquiredImage 0) reserved)
    (submitted, submissionAnswer) <- admitted "submit first frame" (submitFrames [frame] SubmissionAccepted acquired)
    submission <- case submissionAnswer of
      SubmissionRecorded key -> pure key
      answer -> fail (show answer)
    (presented, presentationAnswer) <- admitted "enqueue first presentation" (enqueuePresentation frame PresentationEnqueued submitted)
    presentation <- case presentationAnswer of
      PresentationTracked key -> pure key
      answer -> fail (show answer)
    completed <- admitted_ "complete rendering only" (recordCompletion (atMilliseconds 1) (SubmissionCompleted submission) presented)
    presentationImage presentation completed `shouldSatisfy` maybe False (const True)
    (reservedAgain, nextFrame) <- admitted "reserve a distinct pool record" (reserveFrame target completed)
    _ <- admitted "reacquire image zero while the earlier present fence is pending" (acquireImage nextFrame (AcquiredImage 0) reservedAgain)
    pure ()
```

**Handoff context:**

- **Current behavior:** An old pending presentation record prevents a new
  acquisition of its image even with a free frame slot and separate pool record.
  A future native owner cannot faithfully record that legal successful acquire
  result without first observing the old presentation's retirement.
- **Expected behavior:** Keep image availability distinct from the retirement
  of each presentation's synchronization. A successful reacquisition may use
  fresh reserved synchronization while older present records remain owned.
  Reacquisition must not retire, recycle or discharge those older records.
- **Scope and constraints:** Correct the pure model, its fixture and regression
  expectations, and accompanying contract prose together. Preserve rejection
  of duplicate acquisition while an image is still unpresented and preserve
  explicit unpresented settlement, pool backpressure, distinct pool identities,
  and generation retention. No native implementation is required for this repair.
- **Verification target:** Make the reproduction pass and assert both distinct
  records remain accounted for. Complete and retire repeated uses in legal
  orders and verify that each fact discharges only its own obligations. Keep
  negative cases for unpresented duplicate acquisition and exhausted pools.
- **Deduplication:** The fresh open issue inventory contained only the open
  epics. All-state searches for `reacquisition` and `presentation pool` found
  no repair issue; #155, closed #160 and closed #158 provide design/proof context.
  The claimed ledger row has no prior report/history, and existing review
  reports contain no earlier instance of this finding.
- **Remaining uncertainty:** Native scheduling and fence timing were not
  measured. The verified defect is the pure model's contradiction of the
  accepted input sequence, not a claim of observed native failure.

## 2. Validated configuration opacity

### PRR-2. Prevent public record updates from bypassing GPU budget validation

> **Captured note:** P2 — The public budget module exports the actual record
> selectors of abstract `Budgets`. Ordinary Haskell client code can therefore
> replace validated fields, including the supposedly derived pool capacity,
> without calling `validateBudgets`. Make the validated value read-only through
> public exports and preserve the supported configuration request and readers.

**Verification:** A client importing only exposed modules validates the default
request, performs `validated {progressActionLimit = 0, presentationPoolCapacity = 0}`,
and constructs a model. It compiles and runs against the freshly built pinned
library, exits 0, and prints `(0,0)`. No internal import, unsafe operation,
compiler bypass, or forged identity is involved.

**Evidence:**

- `packages/gpu-vulkan/model/src/Hetoimasia/GPU/Model/Budget.hs:7` promises that
  only `validateBudgets` builds `Budgets`, but lines 21–34 expose the actual
  selectors imported from the internal module.
- `packages/gpu-vulkan/model/src/Hetoimasia/GPU/Model/Internal/Budget.hs:141`
  declares those fields. Hiding the constructor leaves record update available
  through exported field labels. Lines 173–210 enforce positive limits, an
  upper ceiling and a derived pool sum only when validation is called.
- `packages/gpu-vulkan/model/src/Hetoimasia/GPU/Model/Internal/State.hs:464`
  accepts `Budgets` and stores it directly at line 471. The zero pool immediately
  satisfies the exhaustion check at line 1347, and zero progress actions make
  `runProgressTurn` skip every completion/disposal action at line 2117.
- `docs/gpu_model.md:221` and `docs/vulkan_backend_design.md:1499` require
  validation before effects. The pool is specifically derived from the image
  and frame limits, rather than independently writable. Existing budget tests
  verify the validator but contain no external-client record-update rejection.

Save this exact public-only reproduction as `BudgetClient.hs` outside the checkout:

```haskell
module Main (main) where

import Data.Unique (newUnique)
import Hetoimasia.GPU.Model (modelBudgets, newGpuModel)
import Hetoimasia.GPU.Model.Budget
import Hetoimasia.GPU.Model.Identity (sessionIdentity)

main :: IO ()
main = do
  validated <- either (fail . show) pure (validateBudgets defaultBudgetRequest)
  identity <- sessionIdentity <$> newUnique
  let forged = validated {progressActionLimit = 0, presentationPoolCapacity = 0}
      (model, _) = newGpuModel identity forged
  print (progressActionLimit (modelBudgets model), presentationPoolCapacity (modelBudgets model))
```

**Handoff context:**

- **Current behavior:** Values accepted as validated configuration can carry
  zero limits or an inconsistent pool size. The same public update mechanism
  can alter the other supposedly checked fields. Downstream admission and
  progress trust a validation invariant that the public interface does not hold.
- **Expected behavior:** Public clients may edit `BudgetRequest`, validate it,
  and read the resulting configuration. They cannot rewrite fields of a
  validated `Budgets` value outside that validation boundary. Preserve the
  documented reader names and correct checked derivation of pool capacity.
- **Scope and constraints:** Keep this correction within the model's budget
  representation/public boundary, contract documentation and owning tests.
  Preserve editable requests and legitimate small-budget testing. This is an
  API correctness defect, not a claim that the pure library is a security sandbox.
- **Verification target:** Add external-client compile-negative cases for
  updates of each protected budget field, failing because the update is
  inaccessible rather than because package setup is broken. Keep a positive
  client covering request updates, validation, all readers and model creation.
  Existing zero/negative/overflow/derived-sum tests must continue to pass.
- **Deduplication:** All-state searches for `budget record update` and
  `validateBudgets` found no GPU budget repair issue. Closed #47 concerns
  cleanup-failure entries; report `docs/project_review/179.md` concerns Lua
  failure reasons. They are analogous public-boundary defects in different
  types, not duplicate fixes. The claimed PR #175 row has no earlier report.
- **Remaining uncertainty:** None about public update access or acceptance of
  the zero-valued configuration; both were compiled and executed. Other field
  replacements were established from the same exported record representation,
  not individually executed in this review.
