## 1. Native allocation budget

### [#367] PRR-1. [P2] D-40 under-reserves VMA's block-to-dedicated fallback

> **Captured note:** D-40 reserves only `max(preferredBlockSize, requestSize)`, but one VMA call can retain a newly opened empty block after a map failure and then successfully allocate dedicated memory. Freeing the returned allocation does not undo the retained block. Correct the contract before downstream work implements this bound.

**Verification:** Confirmed against the pinned tree and its pinned `VulkanMemoryAllocator-0.11.1.0` header with a headless real Vulkan device on macOS. One memory type, one owner thread, an 8 MiB preferred block, and a 4 MiB mapped request follow D-40's two-call sequence. Injecting `VK_ERROR_MEMORY_MAP_FAILED` into the first `vkMapMemory` call makes VMA open an 8 MiB block, retain it, and successfully fall back to a 4 MiB dedicated allocation. Callbacks record 12 MiB opened and held, exceeding the 8 MiB reservation. Freeing the returned allocation leaves 8 MiB held. The failure injection changes only the first map result; allocation/free callbacks observe actual driver memory. No window or rendering session was opened.

**Evidence:**

- `docs/designs/gpu_resource_services_design.md:836–850` — step 3 asserts the maximum is the larger of block size and request size; step 4 treats an excess as impossible and frees the returned allocation after the call.
- `docs/designs/gpu_resource_services_design.md:851–854` — step 5 acknowledges that retained empty blocks remain charged. This makes the excess observable after the suggested rollback, too.
- The exact pinned VMA header has SHA-256 `90ce12fc4a2466235a09ae02905dd0c13aee80c1bbf11b331ab61230c2ceb112`. In `VulkanMemoryAllocator/include/vk_mem_alloc.h`, `VmaBlockVector::CreateBlock` (11817–11884) opens memory and adds the block to `m_Blocks`; `CommitAllocationRequest` (11764–11788) returns a mapping error before committing allocation metadata; `AllocatePage` (11590–11602) returns failure without destroying that newly opened block.
- In the same header, `VmaAllocator_T::AllocateMemoryOfType` (13491–13630) then takes the dedicated fallback at 13602–13625. A request of exactly half the preferred block size does not take the earlier dedicated-preferred path. `AllocateDedicatedMemory` allocates the request's own size, so both native allocations coexist.
- Fresh reproduction output (bytes):

```text
never-allocate result -2, held 0
opened 8388608, held 8388608
opened 4194304, held 12582912
allocating result 0, maps 2, reserve 8388608, opened 12582912, peak 12582912, held 12582912
after request rollback held 8388608
```

**Handoff context:**

- **Current behavior:** The accepted design authorizes an allocating call after reserving 8 MiB in this case, although that call can open 12 MiB before reconciliation. With only 8 MiB of budget remaining, its promised pre-call budget boundary is crossed. The suggested post-call `vmaFreeMemory` frees the dedicated result but leaves the newly opened block. This is a contract defect awaiting production implementation, not a claim that today's engine already executes D-40.
- **Expected behavior:** The pre-call budget rule must cover all native memory that the configured VMA call can open and retain, including failure-driven fallbacks. Reconciliation and rollback must account for every block retained on a failed request; exceeding the reserved amount must not be an ordinary legal VMA path under the contract.
- **Scope and constraints:** Preserve VMA, the single owner thread, the selected memory type, native-block charging, and the held-memory-first attempt. Amend D-40 and the downstream specification that copied its bound, especially [#333](https://github.com/coghex/hetoimasia/issues/333). [#361](https://github.com/coghex/hetoimasia/issues/361) also repeats this budget boundary in the production qualification work. Establish a sound bound or constrain allocation behavior before choosing an implementation; this report does not prescribe a new allocator or reopen D-38/D-39.
- **Verification target:** Reproduce a block allocation followed by map failure and a successful dedicated fallback under the intended production flags. Check callback totals during the call, after rejection/free, and at allocator disposal, with budget headroom between the old bound and the actual total. Also retain the normal held-memory, block, dedicated, and failed-native-allocation cases. The corrected contract and implementation must enforce the budget on each supported path.
- **Deduplication:** The claimed ledger row for #360 had no review history. Open-and-closed tracker searches for `VMA budget`, `VMA map`, and `reservation map` found #333, #361, #330 and historical unrelated items, but no existing report of this retained-block-plus-dedicated failure path. #333 and #361 require the inaccurate rule rather than track its correction. This is a new finding, with no fixed-later or recurrence classification.
- **Remaining uncertainty:** The production VMA integration and its final flags are not yet implemented. A later design may prohibit this fallback or mapped-allocation path; D-40 currently states the bound without that restriction. The reproduction is platform-specific in device setup, but the retained-block and fallback control flow is in the pinned platform-independent VMA header.

## Reproducing PRR-1

Extract the Hackage tarball for `VulkanMemoryAllocator-0.11.1.0` (tarball SHA-256 `7ae824bd29cd443b7b5d8c23509fb5c02bb5f06b23dfc864a7f11d4ee99d6a91`) into a temporary directory. Use its `VulkanMemoryAllocator/include` header directory and the Vulkan SDK include/library directories qualified by `tools/vulkan/run.sh`. Compile the following standalone file with `clang++ -std=c++17 -O2`, those include/library paths, and `-lvulkan`. On the reviewed macOS machine, run with `VK_DRIVER_FILES` naming the qualified prefix's `share/vulkan/icd.d/MoltenVK_icd.json`. The portability extensions below are the macOS device setup; adapt that setup on another platform without changing the allocator settings or fault injection. Exit 0 means the excess was reproduced, not that the budget contract passed.

#define VMA_IMPLEMENTATION
#define NDEBUG
#include "vk_mem_alloc.h"
#include <cstdio>

static unsigned maps=0;
static unsigned long long held=0, peak=0, opened=0;
static VKAPI_ATTR VkResult VKAPI_CALL map_once_fails(VkDevice d,VkDeviceMemory m,VkDeviceSize o,VkDeviceSize s,VkMemoryMapFlags f,void** p) {
  if (++maps == 1) return VK_ERROR_MEMORY_MAP_FAILED;
  return vkMapMemory(d,m,o,s,f,p);
}
static void allocated(VmaAllocator,uint32_t,VkDeviceMemory,VkDeviceSize s,void*) { held+=s;opened+=s;if(held>peak)peak=held; std::printf("opened %llu, held %llu\n",(unsigned long long)s,held); }

int main() {
