## 1. Presentation-pool construction failure

### [#366] PRR-1. Preserve partial presentation-pool ownership and both construction/cleanup failures

> **Captured note:** P2 — `preparePool` publishes its native handles only after
> creating and naming the whole record. Its `onException` cleanup can replace
> the construction failure, stop before destroying the remaining semaphore,
> and leave the uncertain handles absent from every retirement record. Keep
> partial construction owned and preserve the primary failure plus cleanup
> evidence, including when cleanup itself raises.

**Verification:** The pinned implementation creates the render-finished
semaphore, then the present fence, then names both; only the last transaction
inserts their `PoolSync`. If fence creation fails and semaphore destruction
raises, that semaphore has no retained pool entry. If naming fails and fence
destruction raises, `destroyFence fence >> destroySemaphore rendered` skips
the semaphore destruction entirely. In either case `onException` propagates
the cleanup exception instead of the original construction exception. The
acquisition caller then gives the model reservation back and rethrows that
exception; it neither publishes the partial objects nor marks their destruction
uncertain. `rootsCall` only latches device loss, so an ordinary cleanup failure
does not repair the missing ownership or latch a cleanup safety failure.
Subsequent frame retirement enumerates the pool map and cannot see these
objects. This violates the documented uncertain-object retention and
failure-preserving construction contracts.

The fresh base-only probe copied this exception shape, recording each step
in an `IORef`, and ran through the attempt's liveness wrapper with
`/Users/vincentcoghlan/.ghcup/ghc/9.14.1/bin/runghc`. Its result was:

```text
Left user error (cleanup fence failure)
["naming failed","destroy fence failed"]
```

The original naming error and the remaining semaphore cleanup are absent.
The full ownership conclusion comes from the current static trace, rather
than a device experiment or an injected end-to-end test.

**Evidence:**

- `packages/gpu-vulkan/native/src/Hetoimasia/GPU/Vulkan/Native/Internal/Frames/Acquisition.hs:319` — native objects are created before ownership publication; lines 320–322 use fallible `onException` cleanup; lines 323–324 publish only after naming succeeds.
- `packages/gpu-vulkan/native/src/Hetoimasia/GPU/Vulkan/Native/Internal/Frames/Acquisition.hs:158` — a preparation exception gives the frame reservation back, then rethrows; lines 179–182 only update model accounting and existing pool holders.
- `packages/gpu-vulkan/native/src/Hetoimasia/GPU/Vulkan/Native/Roots.hs:903` — `guarded`, also used by `rootsCall` at line 1582, rethrows ordinary failures and latches only device loss.
- `packages/gpu-vulkan/native/src/Hetoimasia/GPU/Vulkan/Native/Internal/Frames/Progress.hs:345` — retirement obtains synchronization objects from the slot and pool maps; unregistered partial pool handles are invisible to it.
- `docs/gpu_backend.md:2256` — presentation-pool objects whose calls raise must remain explicitly uncertain; `AGENTS.md` requires preserving primary and cleanup failures during partial construction.

**Handoff context:**

- **Current behavior:** A failed pool construction can hide its original error and lose ownership of native synchronization objects if a cleanup action also fails. Those handles cannot prevent a later successful retirement claim through the current pool map.
- **Expected behavior:** Every created object remains owned until successful destruction is recorded. Preserve construction failure and all attempted cleanup failures. Record uncertain destruction, close admission appropriately, and retain the dependencies it requires without retrying an uncertain destroy or falsely certifying retirement.
- **Scope and constraints:** The newly added presentation pool is the confirmed PR #291 path. `prepareSlot` immediately above it uses the same construction pattern; inspect that sibling when choosing a coherent repair, without changing successful frame/presentation synchronization. Keep code, package-owned regressions and contract updates in one PR. This is not a request to redesign the native API or add global state.
- **Verification target:** Add headless cases through the owning native suite for a later pool creation/naming failure combined with cleanup failure, including failure of the first cleanup with another object still live. Assert both failure identities, retained handles and dependencies, no retry of uncertain destruction, no subsequent successful retirement certification, and unchanged normal pool reuse. The exception-only probe is insufficient acceptance for the repair.
- **Deduplication:** The claim-held ledger row has no earlier report/history. The complete open issue inventory and all-state searches for pool cleanup, Vulkan construction failure and presentation pools found no issue for this defect. Closed #182 concerns the former proof harness's handle construction, not these production pool records. No issue was created or edited.
- **Remaining uncertainty:** The failure is verified statically and the exception ordering freshly exercised. No native driver failure was induced and no end-to-end fault injection was run; the eventual repair must add that package-owned injected coverage.
