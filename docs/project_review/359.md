## 1. Hiding graphics-attached host windows

### [#368] PRR-1. [P2] Direct owner-thread hide bypasses the graphics presentation hold

> **Captured note:** Apply the hide safety boundary to every supported public execution path for a graphics-attached host window, or refuse paths that cannot honor it. The new hold is installed only by the host's queued-command executor; public direct owner-thread execution on a borrowed host window still reaches native hide without waiting for presentation or recording withdrawal.

**Verification:** Confirmed by a complete current-source control-flow trace and an external client compiled against only the pinned public GLFW and runtime-GLFW libraries. `withGraphicsOwnerHostIn` publicly accepts the caller's scoped session; that caller can create `newWindowCommandHost session 1`. During the session's owner-thread callback, `withHostWindow host target` lends the attached window and `performWindowCommand commands [window] (hideWindowCommand target)` executes the hide. A session-wide command host has no target-scope rejection. Neither this route's owner/liveness checks nor its window-control checks call the graphics attachment protocol.

The unsafe native unmap is proved statically; this review did not run the bypass on Wayland or deliberately hang a driver. PR #359's own retained Wayland evidence establishes why unmapping before an outstanding legacy-FIFO present finishes is unsafe. Its deterministic and real Cocoa checks pass through the protected queued-host route and do not exercise this public alternative.

**Evidence:**

- `packages/glfw/runtime-glfw-core/Hetoimasia/Runtime/GLFW/Internal/Owner/Lifetime.hs:96` — public `withGraphicsOwnerHostIn` receives `Scoped Session`; callers supplying that live session can construct another command host on its owner thread. The public export is in `packages/glfw/runtime-glfw/Hetoimasia/Runtime/GLFW.hs:680`.
- `packages/glfw/runtime-glfw-core/Hetoimasia/Runtime/GLFW/Internal/Host/Windows.hs:113` — `withHostWindow` checks the session owner and borrows the actual hosted window. The borrow prevents retirement, but installs no presentation hold.
- `packages/glfw/model/Hetoimasia/GLFW/Internal/Command.hs:876` and `:908` — `newWindowCommandHost` uses `HostScope`, which accepts every command.
- `packages/glfw/model/Hetoimasia/GLFW/Internal/Command.hs:1346` — `performWindowCommand` checks owner/liveness, closure, and scope, then calls `runCommand` directly.
- `packages/glfw/model/Hetoimasia/GLFW/Internal/Command.hs:1270` and `:1280` — the direct command locates the supplied window and calls `controlWindow`.
- `packages/glfw/model/Hetoimasia/GLFW/Internal/Window/Controls.hs:93` and `:124` — eligibility and capability checks lead to `nativeHideWindow`; the resulting observation is published after the native call.
- `packages/glfw/runtime-glfw-core/Hetoimasia/Runtime/GLFW/Internal/Host/Commands.hs:151` and `:174` — only the queued-host executor adds `beforeUnmapping` and invokes the attachment's `protocolBeforeHide`.
- `packages/glfw/runtime-glfw-core/Hetoimasia/Runtime/GLFW/Internal/Owner/Withhold.hs:71` — the protocol's hold is what waits until the owner is not presenting to this target. Lines 92–107 turn that hold into a withdrawal count even when hide and show both occur between owner steps.
- `packages/glfw/runtime-glfw-core/Hetoimasia/Runtime/GLFW/Internal/Owner/Worker.hs:194` — each backend step consumes those holds and withdrawal counts. The direct hide never creates one.
- Public-API witness, successfully typechecked with GHC 9.14.1 against the pinned build:

```haskell
directHide ∷ WindowCommandHost → WindowHost → WindowId → IO (WindowResult Disposition)
directHide commands host target =
  withHostWindow host target $ \window →
    performWindowCommand commands [window] (hideWindowCommand target)

directCommands ∷ Session → IO WindowCommandHost
directCommands session = newWindowCommandHost session 1
```

**Handoff context:**

- **Current behavior:** A supported owner-thread direct command can hide an attached window while a graphics step is presenting to it. On the affected Wayland legacy-FIFO path this removes the callback needed for progress, leaving the graphics owner blocked and other targets unable to advance. A direct hide followed by show between steps also leaves the withdrawal counter unchanged, so the backend can reuse the pre-hide generation instead of replacing it.
- **Expected behavior:** Every permitted hide of an attached host window must withhold presentation before native unmapping and preserve a withdrawal across a quick hide/show. An execution path that cannot establish that boundary must refuse the operation before the native call. Preserve ordinary direct commands on unattached windows and their owner/liveness and failure contracts.
- **Scope and constraints:** This is a gap in the protection introduced for [#357](https://github.com/coghex/hetoimasia/issues/357), not a claim that its queued-host fix fails. Public custom session/graphics-owner integrations can reach the gap through `withGraphicsOwnerHostIn`; the standard `withVulkanOwnerHost` internally owns its session and does not expose this exact construction directly. Keep dependency boundaries, host-window borrowing, safe generation retirement, and other-target progress. Do not fabricate presentation completion or destroy an unsafe old generation.
- **Verification target:** Through public `withHostWindow` plus `performWindowCommand`, hold a graphics step at a coordinated presentation boundary and prove native hide cannot occur before it completes, or prove a clear refusal before unmapping. Exercise a direct hide/show wholly between owner steps and verify that any allowed hide produces withdrawal/replacement without reclaiming unsignalled presentation. Keep unattached-window direct commands and normal queued-host hide/show coverage. Qualify any native Wayland reproduction through the supported isolated harness.
- **Deduplication:** The claimed #359 ledger row has no completed review or earlier report. Existing project-review reports contain no `performWindowCommand`/direct-hide/beforeUnmapping finding. Open-and-closed tracker searches for `performWindowCommand hide`, `borrowed window graphics hide`, and `hide presenting Wayland` found no correction for this path; the last found only closed #357. This is a new finding, with no repeat, fixed-later, or recurrence classification.
- **Remaining uncertainty:** The review typechecked the public call and proved the bypass by source trace, but did not execute this alternative against a live Wayland compositor. The hang depends on the driver/presentation mode documented by #357. Public custom integrations are affected; applicability to a particular application depends on whether it uses the direct command API for an attached window.
