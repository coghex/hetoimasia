## 1. Bounded child resource ownership

### [#371] PRR-1. Reclaim output readers when a bounded child abandons its pipes

> **Captured note:** P2 — PR #278's bounded child launcher returns when a descendant outside its process group keeps the output pipes open, but leaves its two reader threads and their pipe handles alive. End the launcher's owned readers and release their handles before returning from the abandoned-output path.

**Verification:** Confirmed against `46e6bad6757cc336d5d81e47c211011a713345e6`, using GHC 9.14.1 and the pinned private `Test.GLFW.Native.Child` module. An owned Python child forked a descendant that entered a new session with `os.setsid()`, kept both inherited output pipes open, and waited indefinitely. The direct child printed a success line and exited successfully. The Haskell driver called `launchCommand 0.05`, forced GC after it returned, and compared `GHC.Conc.listThreads` / `threadStatus` with the pre-launch thread list. After the deadline and two five-second grace periods, the launcher returned:

```text
(ChildExpired 5.0e-2 ExitSuccess,"partial success\n")
[(ThreadId 46,ThreadRunning),
 (ThreadId 43,ThreadBlocked BlockedOnMVar),
 (ThreadId 44,ThreadBlocked BlockedOnMVar)]
```

The two blocked threads are the output readers. Their loop still owns the pipe handles, preventing GC from releasing them while the escaped descendant retains the write ends. The driver's `finally` killed its separately tracked escaped descendant; it did not rely on the launcher to own an escaped process. No native session was acquired.

**Evidence:**

- `packages/glfw/native-tests/Test/GLFW/Native/Child.hs:80` — the launcher creates stdout and stderr pipes.
- `packages/glfw/native-tests/Test/GLFW/Native/Child.hs:94` — both readers are forked, but their thread IDs are discarded; their finalizers only mark completion.
- `packages/glfw/native-tests/Test/GLFW/Native/Child.hs:119` — the second grace result is discarded, and the function returns `ChildExpired` once the direct child is reaped, even when neither reader completed.
- `packages/glfw/native-tests/Test/GLFW/Native/Child.hs:125` — the remaining cleanup signals the original process group; it neither cancels the readers nor closes the parent pipe handles.
- `packages/glfw/native-tests/Test/GLFW/Native/Child.hs:128` — a reader continues waiting for or collecting bytes until EOF, retaining its handle and output accumulator after the launch has returned.
- The independently repeated reproduction ran from the detached tree through the installed project-review liveness wrapper, with an attempt-owned driver: `runghc -XGHC2024 -XUnicodeSyntax -ipackages/glfw/native-tests Probe.hs`.

A minimal child for the reproduction is:

```python
import os, signal, sys
child = os.fork()
if child == 0:
    os.setsid()
    open(sys.argv[1], "w").write(str(os.getpid()))
    while True:
        signal.pause()
else:
    print("partial success", flush=True)
```

The driver snapshots `listThreads`, invokes `launchCommand 0.05 "/usr/bin/python3" ["escape.py", "escaped.pid"]`, reads the escaped PID, and inside a `finally`-protected scope calls `performGC` and inspects the additional threads. Its finalizer sends `sigKILL` to that owned escaped PID. Keeping the escape alive until after inspection is essential: killing it first would supply EOF and hide the leak.

**Handoff context:**

- **Current behavior:** The abandoned-output branch bounds the caller's wait but does not end its output readers. Each such launch can leave two blocked threads and their handles alive indefinitely; an escaped writer that resumes writing can also keep the discarded launch's accumulator growing.
- **Expected behavior:** Once output is deliberately abandoned, the launcher owns no surviving output reader or pipe handle. Preserve the child deadline, direct-child reaping, process-group termination and already captured output, and retain `ChildExpired` so partial success output still cannot pass.
- **Scope and constraints:** Local test-harness resource ownership in `Test.GLFW.Native.Child`, introduced by PR #278's output-collection revision `22e966a0636a3f160121a5aa4dd1ae94840773d4`. The later PR #286 / issue #284 corrected zombie detection, not reader cleanup. Do not require this launcher to terminate arbitrary processes that escaped its group; an adversarial regression must separately own and clean up its escaped fixture. Keep checks headless and preserve consent admission.
- **Verification target:** A deterministic package-owned regression holds the output write ends open outside the child's group, observes `ChildExpired` and retained partial output, and establishes that the launcher has reclaimed both readers and parent pipe handles before it returns. The fixture must clean up its escaped process on every exit. Preserve the existing pre-session launcher regressions, including the ordinary same-group descendant, refused/approved launch, and expired/failing success-output cases.
- **Deduplication:** A fresh complete open-issue listing and all-state searches for child reader, child deadline, `"launchCommand"`, and `"pipes" "launcher"` found no issue covering this leak. Closed #284 explicitly leaves `Child.hs`'s deadline and group-kill behavior unchanged and addresses the orphan-reaper race. The claim-held #278 ledger row has no earlier report or review history; this is a new finding, not a repeat.
- **Remaining uncertainty:** The surviving readers were directly observed on macOS; the same unclosed reader path is shared with Linux, but no fresh Linux reproduction was run. Frequency in ordinary native runs was not measured.
