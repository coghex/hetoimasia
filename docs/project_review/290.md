## 1. Frame-slot construction

### [#366] PRR-1. Retain partial frame-slot synchronization and preserve construction/cleanup failures

> **Captured note:** P2 — `prepareSlot` keeps created synchronization handles
> outside the ownership records until construction and naming finish. A
> subsequent failure with failed cleanup can lose those handles, replace the
> original failure and skip cleanup of the remaining objects. Preserve partial
> ownership, primary failure and cleanup evidence through this path.

**Verification:** At the pin, `prepareSlot` first creates the acquisition
semaphore, then a submission fence, then a cleanup fence, and names all three.
Its `SlotSync` enters `framesSlots` only after every step succeeds. If cleanup
fence creation fails, its handler executes `destroyFence fence >>
destroySemaphore acquisition`; a raised fence destruction skips semaphore
destruction and neither handle is published as retained. A naming failure
has the same problem with three already-created objects. Even a first fence
creation failure loses the semaphore's destruction evidence if that cleanup
raises. `onException` then propagates the cleanup exception instead of retaining
the original construction exception. The acquisition caller returns the model
reservation and rethrows; ordinary `rootsCall` exceptions do not latch cleanup
failure. Retirement can see only published slot/pool entries, so these partial
objects cannot withhold successful retirement through those records.

The PR #291 review at the same pin exercised the identical exception shape
with GHC 9.14.1 and recorded `Left user error (cleanup fence failure)` and
`["naming failed","destroy fence failed"]`: the primary naming failure and
later semaphore cleanup were absent. That probe confirms language semantics,
not the full native slot path. The statements about ownership and retirement
are supported by the pinned code trace.

**Evidence:**

- `packages/gpu-vulkan/native/src/Hetoimasia/GPU/Vulkan/Native/Internal/Frames/Acquisition.hs:265` — creates each slot object before publication; lines 267–270 use fallible sequential `onException` cleanup; line 272 inserts the slot only after naming succeeds.
- `packages/gpu-vulkan/native/src/Hetoimasia/GPU/Vulkan/Native/Internal/Frames/Acquisition.hs:158` — preparation failure returns the model reservation and rethrows. Lines 179–182 cannot retain an unpublished native slot.
- `packages/gpu-vulkan/native/src/Hetoimasia/GPU/Vulkan/Native/Roots.hs:903` — the `guarded` implementation used by `rootsCall` rethrows ordinary failures; only device loss is latched there.
- `packages/gpu-vulkan/native/src/Hetoimasia/GPU/Vulkan/Native/Internal/Frames/Progress.hs:345` — retirement enumerates `framesSlots` and `framesPool`; missing partial slot handles are invisible. Destruction of a published slot, by contrast, records uncertainty and cleanup failure at lines 356–364.
- `packages/gpu-vulkan/native/test/Test/GPU/Vulkan/Native/Frames.hs:57` — the acquisition group covers success, native acquisition errors and ordinary reservation return; it supplies no later slot-construction failure combined with cleanup failure.

**Handoff context:**

- **Current behavior:** A later slot construction/naming failure followed by cleanup failure can discard the original error and lose the created objects from retirement accounting. Remaining cleanup can be skipped.
- **Expected behavior:** Own every created object until successful destruction is recorded. Preserve the construction failure and cleanup failures, retain uncertain objects and their dependencies, close admission under the cleanup safety contract, and neither retry uncertain destruction nor certify retirement while ownership remains unresolved.
- **Scope and constraints:** Repair the production slot construction introduced by PR #290, preserving the successful acquire/submit/skip/close contracts and reserved cleanup synchronization. Coordinate the same correction with `docs/project_review/291.md#PRR-1`, which confirms the sibling presentation-pool path. Keep implementation, owning tests and required contract changes together.
- **Verification target:** Package-owned headless fault injection should combine a later slot creation/naming failure with first-cleanup failure, assert both failure identities, retained handles/dependencies, remaining cleanup policy, no uncertain-destroy retry and no successful retirement certification. Check the normal one-slot/two-slot schedules still pass. The base-only exception probe is insufficient repair acceptance.

Refreshed complete open issue inventory and all-state slot synchronization/cleanup/construction searches found no dedicated issue.
