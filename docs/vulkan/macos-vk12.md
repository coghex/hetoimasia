> **Editorial context, added when this evidence was retained.** Everything
> above the "Captured evidence" marker is written by hand; below it are the
> lines the native run printed at its end, the environment section of the

This is the local macOS evidence for issue #225, VK-12's frame acquisition,
submission and safe abandonment, taken as
[docs/validation.md](../validation.md#the-vulkan-groups-local-evidence)
describes: a Darwin plan, then `run.py` for `test.vulkan-headless` and — under
the owner's standing approval for desktop runs an issue needs, carried on the
command as `HETOIMASIA_NATIVE_SESSION=desktop` — `test.vulkan-native`, under
MoltenVK and Cocoa, with the catalog's `--complete` command. Both passed at
commit `2c07254b32e200dced2597d145bc2b6d65228a89`, input identity
`58f357af26c9a77c9c5d28cf4390aca263f163c3946c51a70fe2fa2b165c4cdf`. The plan also selected `test.workflow`, which ran
directly and passed; the floor groups are CI's.

The native group's preparation found the suite already built
(1.041 s), and its watched native execution took
2.762 s against the 30-second watchdog. The receipts
record `Darwin` and the local prefix's own toolchain map — the
MoltenVK 1.4.0 6e9ec5b29689 driver, the layer
`VK_LAYER_KHRONOS_validation 1.3.296 dc6b9c2fd7b6 +synchronization` — and no `ci-image` entry, so neither
can satisfy a Linux plan. The prefix is a private one built for this run with
`tools/native/native.py build`, because the shared prefix predates this
machine's current Command Line Tools and SDK; its `vulkan` and
`native-manifest` identities are therefore its own. Every scenario passed and
the shared session's verdict was clean. The native receipt is the second run of
the group at this commit: the first also passed, and was run again only to keep
its full console output for the report below.

VK-12's case, `vk12-frames`, ran on private roots in its own child process.
Over a 160×120 window's surface it built a capture generation of 320×240 — the
framebuffer's pixels at content scale 2.0 — in `B8G8R8A8_SRGB` (format 50) with
3 images. It acquired a frame through `tryAcquireFrame` at the first attempt,
recorded the triangle and the copy of its image into a readback buffer the host
had filled with a sentinel, and submitted that batch through `submitFrames`:
one `vkResetFences` immediately before one `vkQueueSubmit2`. The readback
refused its bytes until `progressFrames` observed the submission's fence
signalled, and then exposed bytes that were no longer the sentinel. The frame,
never presented, was closed; its render-finished semaphore was consumed by a
cleanup submission made only after its rendering completed, and its image went
back through `vkReleaseSwapchainImagesEXT` only after that cleanup completed.
Two more frames were acquired and skipped, each through a cleanup submission
waiting on its acquisition semaphore and a release, until image 0 — returned
earlier — was acquired again, with the swapchain built once and never rebuilt.
Nothing was presented, every frame settled, and the slot's two semaphores and
two fences were destroyed with nothing pending. No step received a validation
error, with synchronization validation on, and the verdict after the last
teardown callback was clean. The record lists every native call the frames
made, fence status queries aside.

The plan's local worker declaration is the one
[docs/validation.md](../validation.md#a-local-run-and-its-receipt) shows.
